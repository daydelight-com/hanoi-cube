# 運用手順: 本番リセット(プレイデータの開始前初期化)

開発・検証も本番と同じストア(ローカル `server/output/plays.sqlite3` と Firestore の
`plays` コレクション)に書く運用のため(S12後のユーザー決定)、**本番開始直前に一度だけ**
`scripts/reset_plays.py` で両方をセットで初期化する。

- **リセットするのは開発→本番の切り替え時の1回のみ。** 2日目の朝はリセットしない
  (仕様§3.2-2: ランキングは2日間累積・リセットなし)。
- **片側だけの削除は禁止。** SQLite だけ残すと開発プレイがランキングに出続け、その QR は
  永遠に「準備中」になる。スクリプトは Firestore 未構成なら SQLite にも手を付けずに
  エラー終了する。
- Firestore の削除はクライアントからはルールで禁止(firestore.md §3)のため、
  ブースMacのサービスアカウント鍵による Admin SDK 経由でのみ可能。

## 手順(必ずこの順)

1. **サーバー停止**(`make dev` / uvicorn を Ctrl-C で終了)。
   起動中に DB ファイルを消しても、開いているプロセスが古いデータを持ち続けるため不可。
2. **リセット実行**(リポジトリルートに本番の `service-account.json` があれば自動検出される。
   別の鍵を使う場合のみ `HANOI_FIREBASE_CREDENTIALS=<パス>` を付ける):

   ```bash
   cd server && uv run python ../scripts/reset_plays.py
   ```

   削除対象(SQLite のプレイ数・Firestore のドキュメント数と削除先)が表示されるので、
   内容を確認して `yes` を入力する。`yes` 以外を入力すれば何も消さずに中止する。
3. **サーバー起動**(通常の本番起動手順)。SQLite のスキーマは起動時に自動作成される。
   アップロードキューも SQLite 内にあるため、リセット後に開発プレイが本番 Firestore へ
   送られる事故は起きない。

`HANOI_DB_PATH` を変えてサーバーを運用している場合は、スクリプトにも同じ値を
渡す(同じ cwd で実行するか `--db` で絶対パスを指定)。

## 途中失敗時のリカバリ

削除順は SQLite → Firestore。Firestore 側で失敗しても残るのは「SQLite だけ消えた」状態で、
ローカルランキングには影響しない。**原因(ネットワーク・認証)を解消して再実行**すれば
残りが削除されて完了する(再実行は安全)。

## エミュレータでの検証(リハーサル)

```bash
# 1. エミュレータ起動(別ターミナル)
cd cloud && firebase emulators:start --only firestore --project demo-hanoi

# 2. リセット実行
cd server && FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 HANOI_FIREBASE_PROJECT=demo-hanoi \
  uv run python ../scripts/reset_plays.py
```

検証時のサーバー・記録画面の起動構成は docs/handoff/S12.md「次セッションへの注意」を参照。
自動テストは `server/tests/test_reset.py`(セット削除の担保・確認プロンプト)。

## 設営: マットの向きとカメラ側(HANOI_CAMERA_SIDE)

カメラは**常にプレイヤーの反対側**に設置する前提で、ディスプレイは常にプレイヤー視点の
3D表示になる(ws-messages.md §3 の `camera_side`)。

- **基本の置き方**: マットの**待機エリア(タグ202/203側の手前の帯)をプレイヤーに向け**、
  カメラは塔の向こう(マット奥側)に置く。この構成が既定 `back` で、環境変数の設定は不要。
- カメラを待機エリア側に置く設営にする場合は、サーバーを `HANOI_CAMERA_SIDE=front` で
  起動する(ディスプレイが3D視点を180°反転してプレイヤー視点にする)。
- **設定を誤ると画面がプレイヤーから180°逆に見える。** 実CV(`HANOI_CV=real`)は
  キャリブレーション成立時にカメラ位置の実測と設定を照合し、食い違えば
  警告ログ「カメラ側の設定と実測が食い違う」を出すので、設営時にサーバーログを確認する
  (保存済みキャリブレーションの復元時にも照合される)。

## 箱のタグ貼付規約(3D表示の向き連動の前提)

3D表示は実箱の姿勢(どの面が上か・ひっくり返し・回転)をタグから復元して連動する
(`server/app/cv/geometry.py` の `TAG_IN_BOX`)。この復元は、**1つの箱の6枚のタグが
次の相対配置で貼られていること**を前提にする。タグシート
(`scripts/generate_tag_sheet.py`)の印刷ガイドにも同じ規約を記載している。

1. 面1を上にして箱を置き、面2を手前(貼る人側)と決める。
2. 側面は **面2=手前、面3=右、面4=奥、面5=左**。タグ図柄が正立する向きで貼る。
3. 面1は上面に、**図柄の上端が奥(面4側)を向く**向きで貼る。
4. 面6は箱を**手前へ2回倒して**底を上に向け、**図柄の上端が奥を向く**向きで貼る。

- どの物理面を面1にするかは自由(貼った結果がその箱の面番号になる)。
- **面の相対配置(手順1〜2の並び)や図柄上端の向き(手順3〜4)を誤っても、
  位置・盤面判定(スコア)は正常に動く**。影響は3D表示のみで、箱の面テクスチャが
  実物と食い違って見える(例: 実物は面3が正面なのに表示は別の面)。
- ただし**「図柄が正立する向きで貼る」こと自体(シールの面内回転)は位置精度にも必須**。
  大・中箱は面の右上隅貼りのオフセット補正がタグの向き前提のため、90°回して貼ると
  位置が約51mm、180°で約72mmずれ、エリア・塔判定を壊す(`layout.py` のコメント参照)。
- 貼付済みの箱を検証するには、実CVで起動して箱をゆっくり回し、画面の箱が実物と同じ
  面・同じ向きで回ることを確認する。食い違う箱はタグを規約どおりに貼り直す。
