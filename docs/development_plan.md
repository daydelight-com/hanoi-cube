# Hanoi Cube 開発計画書(AIエージェント向け)

本プロジェクトはAIエージェントがセッションを分けて実装する。本書は「各セッションが最小のコンテキストで最高品質のコードを書く」ための計画である。仕様は [specification.md](specification.md)、ゲームルールは [game/hanoi_arrange_rules.md](game/hanoi_arrange_rules.md) を正とする。

## 1. 基本方針

コンテキスト圧迫による品質低下を防ぐため、次の原則で作業を分割する。

1. **1セッション = 1つの完結した成果物**。セッションをまたぐ作業を作らない。迷ったら分割する。
2. **契約ファースト**。モジュール間のインターフェース(データ型・WSメッセージ・関数シグネチャ)を `docs/contracts/` に先に固定する。各セッションは「自分のモジュール+契約」だけ読めば実装でき、他モジュールのコードを読む必要をなくす。
3. **契約の変更は禁止が既定**。どうしても必要なら、変更内容と影響範囲を `docs/handoff/` に明記し、影響を受ける側の修正まで同一セッションで完了させる。
4. **引き継ぎの外部化**。セッション終了時に `docs/handoff/` へ引き継ぎメモを書く。次セッションは「CLAUDE.md → 該当handoff → 契約 → 自分の担当ファイル」の順で読み、リポジトリ全体を読み込まない。
5. **検証の自動化**。`make check`(lint + 型 + テスト)を全セッションの完了条件にする。人手確認に頼る品質保証をしない。
6. **コミットは小さく**。1論理変更=1コミット。セッション終了時に必ずpushする。

## 3. 契約(docs/contracts/)

S0で以下を確定させる。**以降のセッションはこれを読めば他モジュールを読まなくてよい**。

| ファイル | 内容 |
|---|---|
| `board.md` | 盤面表現の正準形。塔=下からのサイズ列(例 `"LMS/-/L"`)、正規化・鏡像・ハッシュの定義 |
| `ws-messages.md` | WSメッセージ全型(`{type, payload}`)。画面状態、箱ストリーム、入力、判定結果、演出トリガー、i18n |
| `cv-interface.md` | CVワーカー→サーバーの検出結果型(タグID・姿勢・論理盤面・安定フラグ)。**モックはこの型を出す** |
| `game-core-api.md` | 判定エンジンの関数シグネチャ(judge, score, dedup, 最短手順)と事前計算テーブルのJSONスキーマ |
| `firestore.md` | plays ドキュメントスキーマ、セキュリティルール、ランキングクエリ |
| `screens.md` | 全画面のIDと遷移表(specification.md §5の機械可読版)。ボタン入力→イベントの対応 |

Python(pydantic)とTS(型定義)は契約mdから両方に写す。乖離したら契約が正。

## 5. セッションの進め方(全セッション共通)

### 開始時

1. `CLAUDE.md` を読む(自動で読み込まれる)。
2. `docs/handoff/` の**直前のセッションのメモだけ**読む。
3. 担当に関係する契約(`docs/contracts/`)を読む。
4. 仕様の該当節(handoffに記載)を読む。**仕様書全文やリポジトリ全体を読まない。**

### 実装中

- 契約に不明点・矛盾を見つけたら、実装で勝手に解釈せず handoff に「要判断」として記録し、妥当なデフォルトを選んで進める(選んだ内容も記録)。
- テストは実装と同じセッションで書く。「後でテスト」は禁止。
- 外部ライブラリ追加は最小限にし、追加したら理由をhandoffに書く。
- **節目で `/super-review` を実行する**(統合レビュー: code-review / codex:review / security-review)。目安: モジュールが完成しその上に依存コードを積む前、契約の凍結・変更の直後、大きなリファクタ後。指摘は検証のうえ修正まで行う。

### 終了時

**`/finish` を実行する**(すべてを内包: super-review → `make check` → handoff更新 → 日本語メッセージでコミット → push)。handoffは「完了したこと / 契約からの逸脱・追加判断 / 既知の問題 / 次セッションへの注意」を300行以内で書く。コミットメッセージ規約は `.claude/skills/finish/SKILL.md` を正とする。

## 6. 品質ゲート

| 対象 | ツール・基準 |
|---|---|
| Python | ruff(lint+format)、mypy strict、pytest。ゲームコアはBFS照合で全512盤面一致 |
| TypeScript | eslint、prettier、`tsc --noEmit`(strict)。契約型の `any` 禁止 |
| 状態機械 | 遷移表の全遷移+不正入力(無効ボタン)のテスト網羅 |
| CV | 録画フィクスチャ(PoCで撮影した動画)に対する回帰テスト |
| 通し | 各フェーズ末にモック/実機での通しプレイをデモとして実施 |

テストが書きにくい設計はその場で直す(判定ロジックにWSを混ぜない、描画に状態遷移を混ぜない)。「動くが密結合」はこのプロジェクトでは品質不合格とする。

## 7. CLAUDE.md に書くこと(S0で作成)

全セッションが最初に読む最小コンテキスト。**50行以内を維持**する。

- プロジェクト一言説明と締切(8/7 / 8/21-22)
- ディレクトリ構成の要約と「契約→handoff→担当ファイルの順で読む。全体を読まない」という規律
- `make check` / `make dev` / `make mock` の使い方
- 絶対規則: 契約変更の手順、テスト同時作成、節目の `/super-review`、終了時の `/finish`(handoff・日本語コミット・pushを内包)

## 8. リスクと逃げ道

- **最大リスクはCV(S7)**。フェーズ1と独立なので、可能なら8/7前でも箱・タグが物理的に用意でき次第、前倒しでS7を実施してよい。
- CVが期日までに安定しない場合の縮退: モックCVをスタッフ操作(キーボード)に置き換えて興行として成立させる(画面・ゲーム性は損なわれない)。この縮退経路が常に動くよう、モックはS0以降も削除しない。
- クラウド(S9)が不調の場合の縮退: ランキングはローカルのみ、QR画面は「後日公開」の案内に差し替え。
