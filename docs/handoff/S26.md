# S26 引き継ぎ: 本番2日目朝の塔A判定抜け対策(塔バンド奥行きを 0.2H→0.25H に拡大)

本番2日目(2026-08-22)開場前の調整記録。症状は「塔Aに置いたとき時々おかしい
(重ね直すと正常に戻る)」。判定帯の手前側マージン不足が原因で、layout.py の
定数1つの拡大+回帰テストで解消。ユーザーが実機で正常動作を確認済み。

## 完了したこと

### 原因の特定(実測ベース)

`/ws/display` を購読して箱の生座標を集計した結果:

- 塔Aの大箱(large-1、面[3,5]が可視)は安定検出されているのに推定位置が
  (x=83, y=141〜156) と塔中心(105, 207.9)より大きく手前に出て、**塔バンド手前端
  148.5 をまたいでチラつき**(area=None が 418フレーム中 174)。B/C の箱は y≈185 で正常。
- 箱を入れ替える実験で切り分け: 同じ箱は B では (211, 183) で正常、別の大箱は A でも
  (96, 183) で正常、元の箱を A に戻すと再現。→ **箱の個体×Aから見える角度の組合せ**で
  面4のタグの姿勢推定が手前方向に約30mmずれる(layout.py 注記の「タグ図柄のずれで
  面中心オフセット方向が狂い大箱で最大約50mm」と同型)。根治は困難。
- 一般に実機では接地箱の推定yが塔中心より約20mm手前(y≈185)に出ており、0.2H の帯
  (下端148.5)では手前側マージンが37mmしかなく、上記のような個体差で抜けていた。

### 変更

- `server/app/cv/layout.py`: `TOWER_HALF_Y_MM = _H * 0.2` → `_H * 0.25`。
  A3: 帯 ±59.4 → ±74.25(下端 148.5 → 133.7)、`STAGING_Y_MAX_MM` は連動で
  118.5 → 103.6(不感帯30mmは維持)。600x400(テスト前提)では ±80→±100、
  待機帯上限 170→150。docstring の導出値記述を更新。
- `server/tests/test_layout.py`: tower_half_y のダンプを追加し、A3既定で帯の手前端が
  観測最小値 y=141 を含むこと・不感帯30mm・待機帯に大箱が収まることの回帰テストを追加。
- 影響確認: 契約(cv-interface.md)・仕様・フロント layout.ts に帯幅の規定/写しなし。
  モックの待機位置 STAGING_Y_MM=0.2H(59.4)は新上限103.6の内側で不変。
  `make check` 全通過(server 208 / frontend 128 / cloud 12)。
- 実機検証: 反映後 430フレーム連続で A/B/C とも L0 判定、盤面 L/L/L。

## 契約からの逸脱・追加判断

- なし(契約に帯幅の数値規定なし。エリア分類の式は変えず係数のみ変更)。
- 要判断として記録: 実機では塔の置き位置が塔中心より約20mm手前に出る(マット印刷の
  塔枠位置か推定バイアスか未確認)。`TOWER_Y_MM=0.7H` 自体を手前に寄せる案もあるが、
  表示・モック・待機帯に波及するため今回は帯拡大のみとした。

## 既知の問題

- 塔バンド拡大により、塔枠の手前 134〜148mm に置いた箱も塔扱いになる(従来は不感帯)。
  待機帯(〜103.6)との間に30mm不感帯は残るため、待機→塔の誤遷移リスクは従来同等。
- 特定の箱×角度の位置バイアス(約30mm)は残存。帯拡大で判定は通るが、会期後に
  各箱の面ごとのタグ印刷位置・向きを実測して tag_master/FACE_CENTER_OFFSET との
  整合を確認することを推奨(S25 の恒久課題と合わせて)。
