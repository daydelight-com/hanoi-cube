# S12 引き継ぎ: クラウド(SQLite永続化・アップロードキュー・記録画面)

## 完了したこと

- **SQLite永続化**(`server/app/state/sqlite_store.py` 新規): 仕様§7.1 のスキーマ
  (plays / judgements、`uploaded` フラグ)で `PlayStore` 準拠。`main.py` で
  MemoryStore から差し替え済み(MemoryStore はテスト用に残置)。
  DBパスは `HANOI_DB_PATH`(既定 `output/plays.sqlite3`、テストは `:memory:` に隔離)。
  保存は同一IDの全置換で冪等、保存と同時に uploaded=0 でキュー投入になる
- **アップロードキュー**(`server/app/cloud/uploader.py` 新規): Firebase Admin SDK で
  `plays/{play_id}` へ `set()`(冪等)。uploaded=0 を保存順に送り、失敗したら
  その周は打ち切って指数バックオフ(3s→最大60s)で再試行。キューはSQLite上に
  あるためプロセス再起動でも失われない。認証は `HANOI_FIREBASE_CREDENTIALS`
  (または標準ADC `GOOGLE_APPLICATION_CREDENTIALS`)、エミュレータは
  `FIRESTORE_EMULATOR_HOST` + `HANOI_FIREBASE_PROJECT`。未設定・初期化失敗時は
  アップロード無効のままローカルのみで起動する(仕様§3.2-1)
- **記録画面**(`cloud/record/src/` 全面実装、仕様§5.10): Firestore Web SDK(lite)で
  1ドキュメント読取。判定履歴カード(scored=点数+タップで最短手順シミュレーション、
  unclearable=×、duplicate=△+タップで元カードへスクロール)、同サイズ箱を
  個体番号バッジで見分けられる盤面SVG、準備中(ドキュメント不存在)・エラー・
  設定なしの各状態、静的OGP。precompute.json は `server/app/core/data/` から
  ビルド時に直接同梱(写しを持たない)。`/records/demo` でFirestoreなしの
  デモ表示ができる(ブースでの動作確認用)。vitest 7件を `make check` に組込み
- **Firestoreルール**: 既存 `cloud/firestore.rules` は契約 §3 と一致。エミュレータで
  「plays 読取=許可 / クライアント書込=拒否 / 他コレクション=拒否」を実証した
- **QR発行**: 既存実装(S9)のまま。通し検証でQR画面の URL/play_id 発行を確認
- **通し検証(DoD)**: Firestoreエミュレータ停止状態でサーバー起動→モックCV+WSで
  実プレイ(L/MS/L 60点)→ローカル保存・ランキング・QRまで**ゲームは止まらず**完走
  →エミュレータ起動+サーバー再起動→SQLiteに残ったキューがリトライで届く
  →記録画面(エミュレータ接続の実Firestore読取)をブラウザ(モバイル幅)で閲覧、
  シミュレーション15手再生・△スクロール・準備中表示まで確認した。
  `.claude/launch.json` に `record-dev` / `record-dev-emulator` 構成を追加

| `firestore.md` §1 | `judgements[].tower_box_ids` を配列3本のタプルから **a/b/c キーのマップ**に変更。**Firestoreは配列の直接入れ子を保存できない**(実アップロードが `400 Cannot convert an array value in an array value` で恒久失敗する)ことがエミュレータ通し検証で発覚したため。アップローダ(Python)と記録画面(TS `contracts/play.ts`)の両側を同一セッションで追従済み。他契約(cv-interface / ws-messages / SQLite の JSON)は3配列タプルのまま変更なし |

1. **ランキングのクラウド優先読み(仕様§3.2-2)は未実装**。ランキング表示は従来どおり

## 既知の問題・未検証(要人間確認)

1. **実Firebaseプロジェクトが未作成**。本番デプロイ手順が丸ごと未実施:
   プロジェクト作成 → サービスアカウント鍵発行 → `firebase deploy --only firestore,hosting`
   (cloud/ で。rules と indexes は定義済み)→ 記録画面のビルド時に
   `VITE_FIREBASE_PROJECT_ID` / `VITE_FIREBASE_API_KEY` を注入 →
   ブースMacに `HANOI_FIREBASE_CREDENTIALS` と `HANOI_RECORD_URL_BASE`
   (本番Hosting URL。既定はまだ `hanoi-cube.example.com` のプレースホルダ)を設定
2. **スマホ実機での記録画面閲覧は未検証**(内蔵ブラウザのモバイル幅375pxで代替確認)。
   実機QR読取→表示の確認は本番Firebase構築後に行うこと
3. アップロード失敗時のgRPCタイムアウトが1試行あたり最大60秒(SDK既定)。
   バックオフと合わせ、オフライン復帰から反映まで最大2分程度かかりうる。
   会場での体感が問題になるなら `set()` に短いタイムアウトを渡す調整余地あり
4. 管理画面(§5.11)の「アップロードキューの状態と手動再送」は未実装のまま
   (S10の管理画面スコープにも含まれていなかった。キュー自体は自動再送する)

## 次セッションへの注意

- Firestoreエミュレータでの通し再現手順: `cd cloud && firebase emulators:start --only
  firestore --project demo-hanoi`(firebase.json で UI 無効化済み。UI有効だと
  環境によってUIプロセスの起動失敗で全体が落ちる)→ サーバーを
  `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 HANOI_FIREBASE_PROJECT=demo-hanoi` で起動
  → 記録画面は launch.json の `record-dev-emulator`(ポート5175)
- 記録画面の precompute.json はリポジトリ相対 import(`../../../../server/app/core/data/`)。
  テーブルを再生成したら記録画面のビルドにも自動反映されるが、`min_path` の形が
  変わる場合は `contracts/precompute.ts` の型も追従が必要
- 記録画面のスクロールは `scrollIntoView` の `behavior:'smooth'` が環境により
  無動作になる(検証時の内蔵ブラウザで再現)ため即時スクロールにしてある。
  smooth に戻す場合は実機で必ず確認すること
