# S13 引き継ぎ: 本番リセット運用(プレイデータの開始前リセット)

## 完了したこと

- **リセット本体**(`server/app/cloud/reset.py` 新規): ローカルSQLite(ファイルを
  WAL/SHM 副ファイルごと削除)+ Firestore `plays` 全ドキュメント削除。接続構成は
  アップローダと同じ環境変数(`HANOI_FIREBASE_CREDENTIALS` / `FIRESTORE_EMULATOR_HOST`
  + `HANOI_FIREBASE_PROJECT`)。クライアント作成は `uploader.make_firestore_client()`
  に共通化(FirestoreSink も同関数を使用。挙動変更なし)
- **CLI**(`scripts/reset_plays.py` 新規): 薄い入口のみで、本体(引数解析・件数表示・
  `yes` 確認プロンプト・終了コード)は `reset.run_cli()` としてテスト・mypy strict の
  対象に置いた。削除先(エミュレータ/本番+鍵パス)を確認表示に含め誤対象実行を防ぐ。
  `--db` でDBパス上書き。確認プロンプトは**省略不可**(自動実行は `printf 'yes\n' |`
  で標準入力から渡す。当初あった `--yes` フラグは super-review の指摘
  「要件は件数表示→yes入力の確認」を受けて削除した)
- **セット削除の担保**:
  - Firestore 未構成なら SQLite にも手を付けずエラー終了(exit 2)
  - 事前確認(件数取得)に失敗した場合も何も消さずに中止(exit 2)。SQLite の
    「テーブルなし」だけを 0 件扱いとし、ロック(サーバー起動中の疑い)・破損は
    0 件と誤表示せず中止する(super-review の指摘を反映)
  - 削除順は **SQLite → Firestore**。ローカル削除失敗なら Firestore 無傷。
    Firestore 側失敗で残るのは「SQLiteだけ消えた」状態(ローカルランキングに実害なし)
    で、再実行すれば完了する(exit 3 + リカバリ案内を表示)
  - 以上を `server/tests/test_reset.py`(10件)で検証。`make check` 通過
    (server 174 / frontend 104 / cloud 7)
- **運用手順書**(`docs/operations.md` 新規): サーバー停止→リセット→起動の手順、
  2日目の朝はリセットしないこと(仕様§3.2-2)、途中失敗時のリカバリ、
  エミュレータでのリハーサル手順
- **DoD通し検証(Firestoreエミュレータ)**: 開発プレイ2件を一時SQLite+エミュレータへ
  投入 → `scripts/reset_plays.py` を実プロンプト(`yes` 入力)で実行 → 両ストア空を確認
  (`no` 入力での中止も確認)→ 空の状態からサーバー起動(`/api/ranking` が空)→
  モックCV+WSで実プレイ完走(L/MS/L 判定 60点、名前「ほんばん」)→ SQLite に
  uploaded=1 で保存・エミュレータ Firestore に同 play_id のドキュメント到達 →
  記録画面(record-dev-emulator :5175)で `/records/{play_id}` を閲覧し
  名前・60てん・判定カード表示を確認

## 要判断として選んだデフォルト(CLAUDE.md 規則3)

1. **削除順は SQLite → Firestore**(逆順だと Firestore 側失敗時に「SQLiteだけ残る」=
   開発プレイがランキングに出続けQRが永遠に準備中、という悪い状態に陥るため。
   S12申し送りの実害評価に基づく)
2. Firestore の削除はドキュメント単位の逐次 delete(2日分でも高々数百件想定のため
   バッチ化しない)。`plays` 以外のコレクションには触れない
3. 確認プロンプトは `yes` 完全一致のみ実行(前後空白は許容)。それ以外は何もせず中止
