# S8 引き継ぎ: CV本実装

## 完了したこと

cv-interface 準拠の実CV一式を実装し、モックと差し替え可能にした(`HANOI_CV=real` で切替、
既定は従来どおりモック=縮退経路)。無人セッションのため実箱・実カメラは未検証で、
**合成3Dシーン・合成動画による代替検証**でDoDを可能な範囲まで満たした(残項目は下記)。

- `server/app/cv/layout.py` — マット座標系レイアウト定数の正(モック・実CV・エリア分類で共有。
  フロント `frontend/src/three/layout.ts` は同値の写し)。**マット四隅タグ中心位置
  (四隅から30mm内側)は設計値。マット印刷物の作成時にここと一致させること**
- `server/app/cv/tag_master.py` — output/tag_master.json の読込(ID→箱・サイズ・面・黒枠実寸)。
  欠落時は明示エラー(受理条件がマスタ照合を含むため)
- `server/app/cv/geometry.py` — 幾何の中核:
  - マット四隅タグ4枚(計16コーナー)からホモグラフィ→**焦点距離の自己推定**
    (主点=画像中心を仮定、Zhangの拘束)→カメラ姿勢分解。連係カメラは内部パラメータが
    取れないため。合成実測で焦点距離誤差0.2%・カメラ位置誤差2mm
  - タグ1枚の姿勢は `cv2.SOLVEPNP_IPPE_SQUARE`。**汎用ホモグラフィ分解は不採用**
    (黒枠41pxではコーナー0.5pxのノイズで奥行き誤差数百mm。IPPEなら中央値5〜8mm)
  - 箱底面中心の解決: 右上隅貼りの面内オフセット補正+面法線を鉛直/水平へスナップ
    (IPPEの2解曖昧性を物理制約で吸収)。合成シーンで最悪誤差2.2mm(回転箱含む)
  - ヨー(鉛直軸回転)は **mod 90° でのみ推定**(タグ→物理面の貼付対応が不定なため。
    立方体の表示にはこれで十分)
- `server/app/cv/detector.py` — pupil-apriltags ラッパ。設定・受理条件は docs/cv_poc.md §4 の
  決定値(`hamming<=1 かつ margin>=15 かつ ID∈マスタ`)
- `server/app/cv/tracker.py` — 純ロジックの盤面構成:
  - エリア分類(塔バンド±70mm×±80mm、待機=手前170mm以内かつ接地)、z順スタック構成
    +浮遊箱除外(±25mm)、違反検出(モックと `violations_for` を共有)
  - ロスト保持2秒(仕様§4.2)、安定判定0.3秒+最少2フレーム(§4.1-6)、
    位置のEMA平滑化(§4.1-6。100mm超の変位はスナップ)
  - **構造遮蔽保持**: 確定盤面で塔にあった箱は、上に箱が「接して載っている」間は2秒を
    超えても保持(§4.2「確定していた箱は動いていない」)。覆いが浮いたら解放、
    保持スロットに観測箱が重なったら矛盾として解放。
    ※「小の上に大」違反では下の小箱がオーバーハングで**恒久的に隠れる**(合成レンダで実証)
    ため、この推定が違反検出の成立条件になっている
  - 確定盤面は公開内容(サイズ列+待機ID)が変わったときのみ emit(契約§3)
- `server/app/cv/pipeline.py` — 検出→キャリブレーション→幾何→tracker の1フレーム処理。
  四隅コーナーは**フレームを跨いで蓄積**(全箱待機時は手前隅が箱に遮蔽され、同一フレームで
  4隅そろわないため)。再投影誤差3px超の推定は棄却し古い観測を破棄(カメラ微動対策)
- `server/app/cv/worker.py` — 別プロセスワーカー(仕様§3.2)。カメラ/動画→検出→キュー。
  確定盤面イベントは無損失(送れるまで保持・その間フレーム抑止で時系列順を維持)、
  フレームは満杯時に破棄
- `server/app/cv/real.py` — `RealCv(CvSource)`。spawn起動・poll でキュー回収(フレームは
  最新1件に間引き、盤面は全件)・ワーカー死活監視と3秒バックオフ再起動
- `server/app/api/main.py` — `HANOI_CV=mock(既定)|real` で切替。real 時の環境変数:
  `HANOI_CV_CAMERA / HANOI_CV_VIDEO / HANOI_CV_WIDTH / HANOI_CV_HEIGHT / HANOI_TAG_MASTER`
- テスト(計136、全パス): 幾何単体・tracker単体(境界含む)・受理条件境界・
  パイプライン統合(実検出器×合成3Dレンダラ)・**E2E通しプレイ**(下記)

## DoD検証(無人実行での代替)

- 「実箱でS5の通しプレイが成立」→ `server/tests/test_cv_e2e.py`:
  通しプレイを演じる合成動画(1080p・MJPG圧縮・本番相当幾何 2.5px/mm・俯瞰40°)を

- 「ルール違反検出」→ 「小の上に大」を実レンダリング(下箱は実際に隠れる)で検出・
  違反保持・解消まで検証。duplicate_size / overflow は tracker 単体で検証
- 「遮蔽保持」→ 移動中全ロスト(露出1/60s相当)・積み箱の1秒遮蔽・構造遮蔽の
  無期限保持と解放条件を検証
- スループット: 検出+幾何+盤面構成の全体で **7.3ms/frame**(1080p・21タグ・開発Mac、
  30fps予算33msに対し余裕)。ただし合成画像は実写より検出が速い傾向。
  カメラ取得・実写ノイズ込みの再計測は実機で(cv_poc.md §5-4)

## 契約からの逸脱・追加判断

- 契約(docs/contracts/)の変更なし。以下は「要判断」として選んだデフォルト:
  1. **quat はヨー(mod 90°)のみ**(単位quatから改善)。タグID→物理面の貼付対応が原理的に
     不定なため、ひっくり返し・傾きの姿勢は追わない(表示は位置+ヨーで成立)。
     フロント `three/faces.ts` の面対応との突き合わせは実機フェーズで
  2. **一度も観測していない箱**はモックと同じ待機レイアウトのプレースホルダ位置で
     `visible=false, area=null` を送る(契約は常に9箱を要求。起動直後のみ発生)
  3. **2秒超ロスト後も CvFrame は最終位置を送り続ける**(契約§2「常に9箱(ロスト中も
     保持位置で含める)」に従う。area=null になるので盤面には影響しない)
  4. ワーカー再起動時(カメラ切断)は tracker が初期化され、初回確定盤面を再送する
     (契約「起動後の最初の確定盤面」の再解釈。状態機械は冪等に処理するので実害なし)
  5. cv-interface.md §2 の「モックは固定レイアウト(mock.py 冒頭の定数)」という記述は
     定数移動(layout.py)で**参照先だけ古くなった**(意味は不変)。契約変更禁止の既定に
     従い md は触っていない。次に契約を改訂する機会に直す
