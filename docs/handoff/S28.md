# S28 引き継ぎ: OSS ライセンス整備(Apache-2.0)

ユーザー判断「リポジトリは public のままにし、ライセンスを登録する」を受け、Apache License 2.0 での
公開に必要なファイルを整備した。**コード・契約(`docs/contracts/`)・仕様書の変更は一切していない**
(差分はライセンスと帰属表示のテキストのみ)。

## 前提となった判断(ユーザー確認済み)

| 論点 | 結論 |
|---|---|
| public / private | **public のまま**。秘密情報の混入がないことを確認済み(下記) |
| ライセンス | **Apache-2.0**。MIT より企業法務が通しやすく、特許条項が防御に働く点を評価 |
| 適用範囲 | **コードのみ**。ゲームデザイン文書・素材・名称/ロゴは権利留保 |
| 著作権名義 | **Day Delight Inc.**(会社名義)。※正式表記は下記「要判断」参照 |

前提として、ゲームのルールやアイデア自体は著作権の保護対象ではないため、ライセンスで
守れるのは「このリポジトリのコードと素材の再利用条件」だけである(ユーザーに説明済み)。

## 既知の問題・要判断

1. **【要確認】会社の正式表記** — `Day Delight Inc.` は GitHub 組織の表示名から取得した。
   登記上の正式名称(`株式会社◯◯` 等)が異なる場合は `NOTICE` 2 行目・`README.md` の
   ライセンス節(2 箇所)を差し替えること。3 行の修正で済む。
2. **【要確認】社内での追認** — リポジトリが会社組織下にありコミットの大半が会社メールのため、
   職務著作である前提で会社名義とした。公開ライセンスの付与自体は法務 / OSS ポリシー側の
   追認を取ることが望ましい(ユーザーに伝達済み)。
3. **ソースファイルへのライセンスヘッダは未挿入** — Apache 推奨だが必須ではなく、
   全ファイルに触れる差分になるため見送った。必要なら別セッションで。
4. **CLA / CONTRIBUTING は未整備** — 社外からの PR を受け入れる場合、将来のライセンス変更や
   商用ライセンス提供の自由度を保つために必要になる。現状は社内メンバーのみのため未対応。
5. **【未修正】同梱 wheel の SBOM にビルド端末のローカルパスが残っている** —
   `pyxel-3.0.0-...whl` 内の SBOM に `file:///Users/ddl_pc050/workspace/pyxel-cube/crates/...` が
   2 箇所記録されている。鍵やトークンではないが、public リポジトリに端末のユーザー名が
   出ている状態。解消には wheel の再ビルドが必要で、ランタイム更新は仕様書 §8.2 の担当者のみが
   行う取り決め(計画書 §6)のため本セッションでは手を付けていない。次回ランタイムを
   再ビルドする際に併せて解消すること。
