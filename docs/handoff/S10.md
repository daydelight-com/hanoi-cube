# S10 引き継ぎ: クリア条件2の解釈修正(箱の個体で判定)と判定履歴への個体記録

## 背景(不具合の発見経緯)

実機で枚数 (3,2,3) の並び(`LMS/LM/LMS`)が失敗判定になる、という報告から調査した。
実装はルールブック§5 条件2を「最終盤面 ≠ 初期盤面」= **盤面文字列(サイズ列)の比較**で
判定していたが、意図されたルールは「少なくとも1枚の円盤が初期状態とは別の塔にある」=
**箱の個体での比較**だった。同サイズの箱は盤面文字列では区別できないため、
「同サイズの箱を塔間で入れ替えただけの盤面」を "変化なし" として弾いていた。

`LMS/LM/LMS` はA塔の小とC塔の小を入れ替えれば3手でクリアできる(盤面文字列は同一のまま)。

## 変更した契約(絶対規則1に基づく記録)

| 契約 | 変更内容 |
|---|---|
| `game-core-api.md` §4 | クリア条件2を個体基準に変更。検算値 231/119/839 → **304/166/1556**。重複判定に個体を使わないことを明記 |
| `cv-interface.md` §3 | `CvBoardUpdate` に `tower_box_ids` を追加。**再送抑止の判定に個体を含める**ことを明記 |

| `ws-messages.md` §1 | display への `board` payload に `tower_box_ids` を追記(実装は `model_dump(exclude={"kind"})` なので元々含まれていた。契約側の追従漏れ) |

ルールの正 `docs/game/hanoi_arrange_rules.md` §5 も条件2の記述を差し替え、
(3,2,3) のクリア例と「合法手が1手も無い」クリア不可例を追加した。§6 に
「重複判定はサイズと並びだけで行う(個体は見ない)」を明記(§5 と扱いが異なる点)。

## 実装

- `server/app/core/precompute.py` — BFSの状態を個体ラベル付き(`_Boxes`)に変更。
  ゴール条件2を「初期と別の塔にいる箱が1個以上」に。個体割り当ては同型なので
  代表割り当て1通りでよく、**テーブルは512件のまま**(スキーマ変更なし)
- `server/app/core/data/precompute.json` — 再生成(304/512 clearable)
- `scripts/generate_score_ranking.py`(新規)— `docs/game/score_ranking.md` の生成器。
  従来この一覧は手生成で代表の選び方・並び順が不定だったため、
  **代表=canonical_key / 得点降順→円盤数昇順→正準キー辞書順**に定義し直して再生成した
  (166クラス)。実行は `cd server && uv run python ../scripts/generate_score_ranking.py`
- `server/app/cv/interface.py` — `CvBoardUpdate.tower_box_ids`(必須)。
  サイズ列が `towers` と一致すること、同じ箱が複数エリアに現れないことを検証
- `server/app/cv/tracker.py` / `mock.py` — **再送抑止の比較対象をサイズ列から個体列に変更**。
  これが無いと同サイズの入れ替えが `CvBoardUpdate` として出ず、サーバーが
  入れ替え前の箱構成のまま判定してしまう(今回の変更で最も壊れやすい箇所)
- `server/app/state/store.py` / `machine.py` — `JudgementRecord.tower_box_ids` を追加し、
  判定時の箱構成を記録
- `frontend/src/contracts/cv.ts` — TS写しに `tower_box_ids` を追加
- `frontend/src/i18n/strings.ts` — ルールダイアログ「クリアかのうとは」の文面を、
  「動かした結果」であることが伝わる表現に修正(1ページ3行の制約は維持)

## ゲームバランスへの影響(要確認)

新たにクリア可能になった73盤面はすべて枚数が左右対称(a=c)のもので、
既存のクリア可能盤面の最短手数は1つも変わっていない(純粋な追加)。

- 得点対象 119 → 166クラス、総得点プール 839 → 1556点。
  ルールブック§7の「1分で200点前後が上限の目安」は**再見積もりしていない**。
  新規73件の多くが3手クリアで作りやすいため、上限は上振れする可能性が高い
- 最高得点が 24点 → **30点**(`[大]/[大,中,小]/[中]` と `[大,中]/[大]/[中,小]`、いずれも6手)

## 残課題

1. **記録画面での個体表示は未実装**。`cloud/record/src/` はまだ Vite テンプレートのままで、
   記録画面の実装自体がこれから。データ(`tower_box_ids`)は判定履歴に入るところまで
   done なので、記録画面を作るセッションで「同サイズの箱を色や番号で見分けられる盤面表示」
   と「`min_path` を初期個体に適用した再生」を実装すること。
   `min_path` は `{size, from, to}` のみだが、動かすのは常に from 塔の最上段なので
   個体は一意に定まる(手順データ側に個体IDを持たせる必要はない)
2. **SQLite / Firestore への永続化は未実装**(S9時点でストアはメモリのみ)。
   スキーマは `specification.md` §7.1 / §7.2 と `firestore.md` に
   `tower_box_ids` を追記済みなので、実装時に取りこぼさないこと
3. 表示画面(display)の `judge` ペイロードには個体を載せていない。
   演出で「どの箱が動くか」を出したくなったら `ws-messages.md` §2 の Judge 拡張が必要
4. 「クリア判定は成立するが盤面の見た目が初期状態と同一」という結果は、
   来場者・観客には直感的でない可能性がある。ルールダイアログの文面調整や
   演出での強調は要判断(今回は文面を最小限直すに留めた)
