# S11 引き継ぎ: クリア条件1を「サイズまで含めた左右反転」に変更

## 背景(ゲームデザイン判断)

S10で条件2を個体基準に直した結果、`[大]/[大,中,小]/[中]`(枚数 (1,3,1))のような
「枚数が最初から左右対称で、箱を1個動かして戻すだけ」の配置が高得点(30点)になっていた。
これを受けて条件1の見直しを検討し、**サイズまで含めた左右反転**を採用した。

判断材料として全512盤面で両ルールを計算し比較した(採用理由):

- ルールを一言で言える(「並べた形を左右ひっくり返した形にできればクリア」)。
  ブースで来場者に短時間で説明する必要があるため、これが最大の理由
- 目標が盤面として目に見えるので、判定前に自分で検証でき失敗に納得感がある
- 手数分布に山ができる。旧: 最大7手が1クラスのみ → 新: 7手が12クラス + 15手が1クラス

## 変更した契約(絶対規則1に基づく記録)

| 契約 | 変更内容 |
|---|---|
| `game-core-api.md` §4 | クリア条件1を鏡像一致に変更。検算値 304/166/1556 → **220/124/1282**、最短手数の最大 7手 → **15手**(`L/MS/L`) |

`cv-interface.md` / `firestore.md` / `ws-messages.md` は変更なし(S10の `tower_box_ids` はそのまま有効)。
ルールの正 `docs/game/hanoi_arrange_rules.md` §5 条件1を差し替え、クリア不可の例に
「枚数は反転済みだがサイズ配置を一致させられない」ケースを追加した。

## 実装

  「サイズ列が `mirror_board(board)` と一致」に変更。`_size_towers()` を追加。
  条件2(個体で1個以上が別の塔)はS10のまま据え置き
- `server/app/core/data/precompute.json` — 再生成(220/512 clearable)
- `docs/game/score_ranking.md` — 生成器で再生成(124クラス)
- `frontend/src/i18n/strings.ts` — ルールダイアログ「クリアかのうとは」を
  「ならべた かたちを ひだりみぎ ひっくりかえした かたちに うごかせたら クリア!」に変更。
  条件2の注記(「さいしょから おなじ かたちでも 1こは うごかそう」)を4行目に追加した。
  他ページは3行だがダイアログは `minHeight` 指定なので4行でも崩れない
  (ja/en 双方をブラウザで実表示して確認済み)

## 数値の変化

| | 旧(枚数の反転) | 新(サイズまで反転) |
|---|---:|---:|
| クリア可能 | 304/512 | 220/512 |
| 得点対象クラス | 166 | 124 |
| 総得点プール | 1556点 | 1282点 |
| 最短手数の最大 | 7手 | **15手**(`L/MS/L`) |
| 最高得点 | 30点 | **60点**(`L/MS/L` = 4箱×15手) |

新ルールは旧ルールの**真部分集合**で、新たにクリア可能になる盤面はゼロ。
クリア不可になったのは42クラス、両方クリア可能で手数が増えたのは17クラス。

## テスト(server 153件 / frontend 104件、`make check` 通過)

- `test_precompute.py` — 独立BFSのゴールも `mirror_board()` から独立に構成し直した
  (実装の `_size_towers()` を使わない)。検算値・15手の唯一性を検証。
  「枚数は反転済みだが鏡像にはできない」`L/LMS/M` `LMS/MS/L` のクリア不可を明示的に検証
- `test_engine.py` — 得点1位が `L/MS/L` の60点(4箱×15手)に変わったのを反映。
  ルールブック§5の3手クリア例 `LMS/LM/L` は新ルールでも3手のまま(終盤面が元々鏡像だった)
- `test_state_machine.py` / `test_cv_e2e.py` — 共有定数 `SCORED_POINTS` を 24 → 60 に更新

モックCV経由の手動確認: `L/MS/L` → scored 60点(15手)、`L/LMS/M` → unclearable、
`LM/LS/LM` → scored 42点。

## 既知の問題・要判断

1. **得点上限の目安が未計測**。ルールブック§7から「1分で200点前後」の記述を外した。
   総プールは減ったが1配置あたりの単価が上がったため、当日のバランスは実測が要る
2. **効果音のノート数しきい値** `successNoteCount = min(8, 4 + points/10)` は
   旧ルールでは上限8に到達しなかった(最大30点=7音)。新ルールでは42点・60点で
   8音に到達する。演出としては問題ないと判断したが、意図した設計ではない
3. **難易度が上がる**。適当に並べて当たる確率が 59% → 43% に低下。同点時の順位第2キーが
   失敗回数なので、初心者に厳しくなる方向。練習モードでの慣らしがより重要になる
4. `docs/development_plan.md` §4 S1行のDoD記述に「24点配置」とあるが、これは完了済み
   セッションの記録なので書き換えていない
5. S10からの繰り越し: 記録画面(`cloud/record/`)は未実装、SQLite/Firestore への
   永続化も未実装。詳細は [S10.md](S10.md) を参照
