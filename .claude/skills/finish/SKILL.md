# finish: セッション終了処理

レビュー済み・検証済みの状態で成果をリポジトリに確定させる。以下をすべて順に実施する。途中で失敗したら解決してから先へ進む(スキップしない)。

## 手順

1. **統合レビュー**: Skillツールで `super-review` を実行する。指摘の修正まで完了させる。直前に super-review を実行済みで、それ以降にコードの変更がない場合のみ省略してよい(省略した場合は報告に明記)。
2. **最終チェック**: `make check` を実行して通す(未整備なら存在するlint・型チェック・テストを直接実行)。
3. **handoff更新**: `docs/handoff/S{n}.md` を作成・更新する(development_plan.md §5 の様式: 完了したこと / 契約からの逸脱・追加判断 / 既知の問題 / 次セッションへの注意。300行以内)。
4. **コミット**: 論理単位ごとに分けてコミットする。無関係な変更を1コミットに混ぜない。
5. **プッシュ**: `git push`。リモートとの競合等で失敗したら解決して再実行する。
6. **報告**: コミット一覧(ハッシュとタイトル)、レビュー結果の要約、残課題を簡潔にまとめる。

## コミットメッセージ規約(日本語)

タイトルと本文を日本語で書き、**何をしたか**が履歴だけで分かるようにする。

```
<タイトル: 何をしたか。50字以内目安>

- <変更内容の要点(何を・なぜ)>
- <影響範囲や設計判断があれば記載>

Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
```

例:

```
判定エンジンに鏡像重複の判定を追加

- 判定済み配置の照合時に左右反転形を同一視するようにした
  (ルールブック§6の「鏡像は同じ配置とみなす」に対応)
- 事前計算テーブルに鏡像代表形のフィールドを追加
- BFS照合テストに鏡像ペアのケースを追加
```

- タイトルは体言止めまたは「〜を追加/修正/変更」の形。「fix」「update」だけの説明にならないこと。
- 本文には変更の理由・仕様との対応を書く。差分を読めば分かること(行の羅列)は書かない。
