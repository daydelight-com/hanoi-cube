# super-review: 統合レビュー

変更差分に3種類のレビューをかけ、確認できた問題を修正するまでがこのスキルの範囲。コミット・プッシュは行わない(それは /finish の役割)。

## 手順

1. **対象範囲の確定**: `git status` と `git diff`(未コミット変更)、および前回レビュー以降にコミット済みの変更があれば `git diff <前回レビュー時点>..HEAD` で範囲を出す。差分が概ね1000行を超える場合は論理単位(モジュール単位)に分け、単位ごとに以下を繰り返す。
2. **3レビューの実行**(順に):
   1. Skillツールで `local-code-review`(ビルトイン /code-review はモデル起動不可のためプロジェクト内スキルで代替)
   2. Codexレビュー: Agentツールで `codex:codex-rescue` エージェントを起動し、
      「対象差分(コミット範囲 or 未コミット)に対する**レビュー専用**パス。差分だけでなく
      影響範囲(変更された関数・型・メッセージの呼び出し元/参照元、壊れうる既存テスト)も
      調査したうえで、修正はせず、指摘を ファイル:行 / 重要度 / 内容 / 根拠 で列挙して返す」
      よう指示する
      (`codex:review` コマンドはモデル起動不可のため。Codex CLI 未設定で失敗した場合は未実施扱い)
   3. Skillツールで `security-review`
   - 実行できなかったレビューはスキップし、最後の報告に「未実施」と明記する。勝手に代替手段で済んだことにしない。
3. **指摘の統合と検証**: 3つの結果を重複排除して一覧化し、各指摘を**コードを読んで自分で検証してから**扱いを決める。
   - 正しい指摘 → 修正する。修正がセッションの担当範囲を超える場合は `docs/handoff/` に記録して見送る。
   - 誤検知・意図的な設計 → 理由を付けて棄却する。
   - `docs/contracts/` の契約に反する実装が見つかった場合は最優先で修正する(契約側を変えたくなったら development_plan.md §1-3 の手順に従う)。
4. **修正後の確認**: `make check`(未整備なら存在するlint・型チェック・テストを直接)を実行して通す。
5. **報告**: 「修正した指摘(要約と対応)/ 棄却した指摘(理由)/ 未実施のレビュー / 残課題」を簡潔にまとめる。

## 使いどころ(エージェントの判断で随時)

- モジュールが一区切りつき、その上に依存するコードを書き始める前
- `docs/contracts/` のインターフェースを確定・変更した直後
- 大きなリファクタや設計変更の後
- /finish の実行時(finishから自動で呼ばれる)

小さな修正のたびに回す必要はない。「この上に積む前に土台を固めたい」タイミングで使う。
