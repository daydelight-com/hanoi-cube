# local-code-review: 変更差分のコードレビュー

ビルトイン `/code-review` はモデルから起動できないため、その代替としてエージェント自身が行う精査手順。
指摘の列挙までがこのスキルの範囲。**修正は行わない**(super-review 側の役割)。

## 手順

1. **範囲確定**: 次のすべてを合わせて対象差分とする。`git status` に名前だけ出た変更を
   内容未確認のまま残さない。
   - `git diff`(未ステージ)と `git diff --cached`(ステージ済み)
   - `git status --short` に出る未追跡ファイル(内容を Read で読む)
   - `git log origin/main..HEAD --oneline` + `git diff origin/main..HEAD`(未プッシュのコミット)
2. **影響範囲の調査(レビュー前に必ず実施)**

   > この手順を省略しない。変更ファイルだけを見てレビューを始めてはならない。

   差分に現れないコードへの影響を Grep / Explore サブエージェントで洗い出し、
   見つかったファイルはレビュー対象に加える:
   - 変更されたクラス・関数・定数を呼び出している既存コード(Python は import 元、
     TS は `frontend/` と `cloud/record/` 双方の参照元)
   - 変更されたスキーマ・データ型を参照している他の箇所(`docs/contracts/` の契約、
     pydantic モデルと TS 写しの両側、SQLite / Firestore スキーマ、precompute.json を読む側)
   - 変更された API・WS メッセージ型を利用しているフロントエンド(display / controller / admin)
     や記録画面、モックCVとの互換性
   - 既存のテストが意図せず壊れる・**壊れずに古い仕様のまま通り続ける**可能性がある箇所
     (テストが参照するフィクスチャ・定数・契約の例示値を含む)
3. **観点別レビュー**(差分が大きい場合は Explore / general-purpose サブエージェントを観点ごとに並行起動する):
   - **正しさ**: ロジックのバグ、境界条件(空盤面・0点・満杯・タイムアップ境界)、例外処理、
     off-by-one、非同期・並行の競合
   - **契約整合**: `docs/contracts/` と実装(Python / TS 写し)の一致。契約内の例示・数値は検算する
   - **仕様整合**: handoff に記載された仕様書該当節・ルールブックとの矛盾
   - **テスト**: 変更に対するテストが同セッションで書かれているか、境界と異常系を踏んでいるか
   - **設計**: 密結合(判定ロジックにWS、描画に状態遷移を混ぜる等。計画§6は密結合を品質不合格とする)、
     重複、不要な複雑さ
4. **検証**: 各指摘は該当コードを実際に読み直して再検証し、誤検知・意図的な設計を落とす。
5. **報告**: 検証済みの指摘を「ファイル:行 / 重要度(High/Med/Low)/ 内容 / 根拠」で列挙する。
   影響範囲の調査で見つけた「差分外の要修正箇所」も同じ形式で含める。指摘ゼロならゼロと明記する。
